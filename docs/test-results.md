## 3. ทดสอบด้วยหน้าจอ (จำลอง flow rootcase — อัปเดต 2026-11-13: 3 แอปเต็มรูป)

ระบบมี **3 แอปมีหน้าจอจริง**: **Central ID Portal** (:3000, Go Fiber — บัญชีกลาง: โปรไฟล์/แอปที่เชื่อมต่อ/session/logout กลาง, client `central-id-portal`, aud `central-id`), **Buyer Portal** (:3010, NestJS), **CIS Portal** (:3020, Go Fiber) และเปิดใช้ **Identity Brokering** (Option B ใน migration-plan): ผู้ใช้ login ที่ realm `central-id-upstream` (**"Central ID จริง" — ธีมเขียว**, จำลองระบบ Central ID เดิม — ตั้งโดย `scripts/setup-brokering.sh`) แล้ว realm `central` (Keycloak ซ่อนเบื้องหลัง) ออก token ให้แอป — ผู้ใช้ไม่เห็นหน้า login ของ realm central เลย ทุกหน้ามีแถบขั้นตอน flow ตาม rootcase: [1] ล็อกอิน Central ID → [2] Buyer Portal → [3] CIS Portal (SSO) → [4] Logout กลาง

ผลจำลองด้วย curl + cookie jar ตาม redirect ทุกขั้นเหมือน browser (2026-11-13):

1. ✅ เปิด Central ID Portal (:3000) → hero "Central ID — บัญชีกลาง" + ปุ่มล็อกอิน
2. ✅ Login → **โดนพาไปหน้า login ของ Central ID จริง** (upstream realm, ธีมเขียว) → กรอกรหัส → auto-link (Detect Existing + Auto Link, ผูก email กับบัญชีเดิมโดยไม่ถาม) → กลับมาเห็น "สวัสดี buyer-user" + token ครบ aud/principal_type/tenant_id
3. ✅ หน้า **แอปที่เชื่อมต่อ**: Buyer Portal / CIS Portal (เชื่อมต่อแล้ว + SSO) / Open API (M2M ไม่แสดง session)
4. ✅ เปิด Buyer Portal → SSO ทันที → dashboard + Orders (GET 200 / POST 201 ผ่าน cookie session)
5. ✅ เปิด CIS Portal → SSO ทันที → dashboard + Projects (GET 200 / POST 200)
6. ✅ **Logout กลาง** จากแอปใดก็ได้ (`client_id` + `id_token_hint` + `post_logout_redirect_uri` ลงทะเบียนครบ → ไม่ขึ้นหน้า confirm แล้วพากลับแอป)
7. ✅ Login ใหม่ที่ CIS → **กลับไปหน้า login ของ Central ID จริง กรอกรหัสจริง** (SSO ถูกยุติ)
8. ✅ **Playwright ถ่ายภาพจริงครบ 15 ขั้น** (ทุกภาพอยู่ที่ `docs/screenshots/` — รันซ้ำได้: `cd tools/screenshots && source ../../.env && node journey.mjs`)

หมายเหตุพฤติกรรมหลังมี brokering: (1) หลัง logout กลาง **access token เดิมยัง valid จน exp** และ session ของ Keycloak ที่ค้างในเครื่องเดิมยังใช้ได้ — production ต้องตั้ง **backchannel logout** จาก Central ID → Keycloak (rootcase §6); (2) logout จากแอปไม่กระทบ SSO session ของ Central ID (สมจริงแบบ Google) — ต้อง logout ที่ Central ID จึงจบทุกระบบ

## 4. สิ่งที่พบระหว่างทดสอบ (2026-11-12 ถึง 2026-11-13)

1. **KC 26 ไม่มี field `keys` บน RealmRepresentation** — import RSA key แบบ static ผ่าน realm.json ใช้ไม่ได้ (สลับไปให้ Keycloak generate เอง + ดึง public key ผ่าน Admin API — ดู ADR-003)
2. **Mapper config key ต้องเป็นเอกพจน์บน KC 26.x** — `access.token.claim` / `id.token.claim` (รูปแบบเอกสารเก่าเป็นพหูพจน์ `access.token.claims` — ไม่มี legacy fallback ใน `OIDCAttributeMapperHelper.includeInAccessToken()` → mapper ถูกข้าม**เงียบ ๆ** ไม่มี log/error) — พิสูจน์จาก source 26.3.5 (`OIDCAttributeMapperHelper.java:386-392`)
3. **Realm import ที่มี `clientScopes` ชัดเจน จะไม่สร้าง stock scopes** (`basic`/`profile`/`email`/`roles`/`web-origins`/`acr`) และ `default-default-client-scopes` ว่าง — บน KC 26 `sub` ของ access token มาจาก **sub mapper ใน scope `basic`** (initToken ตั้ง sub เฉพาะ TRANSIENT session เช่น client_credentials) — realm ที่ import เองต้องใส่ stock scopes ใน template ด้วย (template ปัจจุบันผสมนิยาม stock จริงที่ export จาก realm ที่สร้างสดแล้ว)
4. **`jti` ของ KC 26.x มี prefix บอกบริบท** — รูปแบบ `sessionType+tokenType+grantType:uuid` เช่น `onrtro:` = online+regular, `trrtcc:` = transient+regular+client_credentials, `onltro:` = online+**lightweight** (ไม่ใช่ token เสีย — ดู source `DefaultTokenContextEncoderProvider`)
5. **KC 26 ตั้ง admin-cli/admin-console เป็น lightweight access token โดยดีไซน์** (`RealmManager.java:232` set `USE_LIGHTWEIGHT_ACCESS_TOKEN_ENABLED=true`) — token ของ admin-cli จึงไม่มี `sub`/claims ที่ mapper ไม่ได้ตั้ง `lightweight.claim` — เป็นพฤติกรรม stock ทุกเวอร์ชัน 26.x **ไม่ใช่ bug ของ instance**
6. **Kong 3.9 jwt plugin ใช้ config `key_claim_name`** (ไม่ใช่ `key_claim`) และ `rsa_public_key` ต้องเป็น PEM ที่มี header/footer ครบ — ค่า `publicKey` จาก Admin API เป็น base64 ดิบ ต้องห่อ BEGIN/END ก่อนใส่ kong.yml
7. **PEM จาก openssl บน Windows มี CRLF** — ต้อง normalize เป็น LF ก่อนฝังลงไฟล์ config
8. **YAML block scalar** — public key ใน kong.yml ต้อง indent ลึกกว่า key line (`rsa_public_key: |` ที่ 8 ช่อง → content 10 ช่อง)
9. **git-bash (MSYS) แปลง `/CN=...`, `-w /w` เป็น Windows path** — ใช้ `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL="*"` กับทุกคำสั่งที่ arg ขึ้นต้นด้วย `/`
10. เครื่องนี้ไม่มี jq — scripts มี fallback ไป `ghcr.io/jqlang/jq` ผ่าน docker แล้ว
11. สร้าง user ผ่าน Admin API **ต้องมี email** (ไม่งั้น password grant ล้มเหลวด้วย `resolve_required_actions: Account is not fully set up`) — users ใน central realm import มี email ครบอยู่แล้วจึงไม่กระทบ
12. **สรุป root cause ของอาการ "token ไม่มี sub/aud/claims" ที่ไล่กันทั้งวัน (2026-11-13)** — ไม่ใช่ image ถูกแก้ และไม่ใช่ KC bug เฉพาะเวอร์ชัน แต่คือ 3 ปัจจัยซ้อนกัน: (a) mapper config key พหูพจน์ไม่ตรง constant (ข้อ 2), (b) realm import ล้าง stock scopes ทำให้ไม่มี sub mapper (ข้อ 3), (c) token ทดสอบเทียบส่วนใหญ่มาจาก admin-cli ซึ่งเป็น lightweight โดยดีไซน์ (ข้อ 5) — หลังแก้ (a)+(b) ใน template: token ทุก grant มี `sub`/`aud`/`principal_type`/`tenant_id` ครบ และ suite ผ่าน 57/57
13. **KC 26.3 callback redirect เรียง query เป็น `state → session_state → iss → code`** — script เดิม grep `/auth/callback?code=` จึงไม่ match (แก้ pattern แล้ว); และ**หลัง global logout** KC คืน **200 HTML หน้า login** (มี `login-actions` ใน body) ไม่ใช่ 302 — script ตรวจจาก body
14. **Revocation กับ JWT validation ล้วน** — token ที่ revoke ผ่าน revocation endpoint ยังผ่าน Guard จน exp เพราะ Guard ตรวจ JWKS เท่านั้น (กฎ CLAUDE.md #8) — introspection คือกลไกเดียวที่รู้ revocation (ทดสอบและบันทึกไว้ใน `revocation-test.sh` — production ใช้ token สั้น + introspection เฉพาะ operation เสี่ยงสูง ตาม rootcase §6)

42. **[KC 26] เปิด Standard Token Exchange V2 (RFC 8693) ให้ครบ 4 เงื่อนไข** — (1) requester ต้องเป็น **confidential client** (public โดนปฏิเสธ) (2) ต้องเปิด switch ราย client: attribute **`standard.token.exchange.enabled="true"`** (feature ระดับ server เปิด default แล้วแต่ยังติด "Standard token exchange is not enabled for the requested client" ถ้าลืม) (3) requester ต้องอยู่ใน **aud ของ subject token** (ยกเว้น requester เป็นเจ้าของ token) — จึงมี scope `stt-bridge` เติม `cis-web` ลง aud ของ token ต้นทาง (4) บังคับส่ง **`subject_token_type`** ไม่งั้น error — token ใหม่ได้ aud/scope/claims จาก scopes+mappers ของ requester (cis-api + principal_type + tenant_id ครบ) — ดู ADR-004
43. **[KC 26] Admin API ผูก client scope เข้า client ใช้ PUT บน item path** — `PUT /admin/realms/{r}/clients/{id}/optional-client-scopes/{scopeId}` (204, ไม่ต้องมี body) — **PUT บน collection** (`.../optional-client-scopes`) ไม่มีในระบบ ตอบ **404** ทั้งที่ GET บน path เดียวกันได้ 200 (หลอกตามมาก) — เทียบเคียง: realm-level ใช้ `PUT /default-default-client-scopes/{id}`
44. **[KC] การเลื่อน client เป็น confidential กระทบลูกโซ่ทุก flow ที่แลก code/y grant ด้วย client นั้น** — cis-web เป็น confidential (จำเป็นของ exchange) → token endpoint บังคับ `client_secret` ทันที: CIS app (AC flow), `pwd_token` ใน smoke scripts, sso-test ต้องส่ง secret ครบ — ผิดพลาดจะออกอาการเป็น 401 invalid_client เฉพาะจุดที่ลืม — สอดคล้องหลัก "แก้ contract ต้องไล่แก้ทุกผู้เรียก" ของ repo นี้
45. **[Web] cookie ไม่ผูก port (RFC 6265) = โอกาสของ POC เดียวกัน + ข้อควรระวัง production** — SSO Ticket ทำงานได้เพราะทุกแอปอยู่ host `localhost` ต่าง port เท่านั้น และ browser ส่ง cookie ให้ทุก port (cookie scope ที่ host ไม่ใช่ port) — เป็นสะพานให้แอป embedded login สร้าง "SSO session ของ ID กลาง" ได้โดยไม่แตะ browser flow — production ห้ามพึ่งพาเช่นนี้ข้าม domain ใด ๆ ให้ใช้ subdomain ร่วม (`*.central.com`) โดยตัว ID กลางเป็นผู้ถือ SSO cookie เอง (Universal Login) — และตั๋วเป็น reusable: ต้องมี TTL + revoke ตอน logout + renew ฝั่ง broker (เก็บ refresh token แทน app)
46. **[Arch] Logout กลางแบบ propagate จริง = session ต้องผูกกับตั๋ว + ปลายทางตรวจ liveness** — ปัญหาเดิม: session ของแต่ละแอปเป็น token ใน cookie (มีชีวิตถึง exp ≤5 นาที) การ revoke ตั๋วไม่มีผลย้อนกลับ → กด Logout กลางแล้วแอปอื่นยังใช้ได้ต่อ — แก้ 3 ชั้น: (1) session ที่เกิดจากตั๋วต้องจำตั๋วของตัว (fintech เก็บใน server session, Buyer/CIS เก็บ cookie `sso_bound`) (2) ทุกครั้งที่เปิดหน้า page ปลายทางถาม broker `/sso/check` (in-memory ~ms, fail-open เมื่อ broker ล่ม) → ตั๋วตาย = เคลียร์ session ทันที (3) `POST /sso/logout` = revoke **ทุก** ตั๋ว — ปุ่ม Logout กลางของทุกแอปเรียก — ข้อจำกัดที่ยอมรับ: API request ที่ถือ Bearer อยู่ยังผ่านจน exp (ข้อจำกัด JWT ตาม rootcase §6); authN ยัง verify JWT จาก JWKS เองทุก request (Rule 8 ไม่ถูกละเมิด — /sso/check คือ liveness ของ SSO ไม่ใช่การ verify token) — **production: ใช้ OIDC Back-Channel Logout** (KC attribute `backchannel.logout.url` ต่อ client + แอป validate logout_token) แทน per-request check
47. **[Arch] การผูกตั๋วต้องครบ "ทุกทางเข้า session" ไม่เช่นนั้น logout จะรั่ว** — เคสที่พบจากผู้ใช้จริง: Buyer ที่ได้ session จาก**ปุ่มโอน session (STT `/auth/stt`)** ไม่ผูกตั๋ว (ตอนแรก set `sso_bound` เฉพาะทาง new-tab redeem ที่ `/auth/login`) → Logout กลางแล้ว Buyer ยังอยู่ — แก้: `/auth/stt` ของ Buyer/CIS อ่านตั๋วจาก cookie `central_sso` ที่ browser ส่งมาด้วยแล้ว set `sso_bound` ให้ — บทเรียน: ทุกทางเข้า session (login/redeem/transfer) ต้อง bind ตัวตนกับ SSO artifact เดียวกัน ไม่งั้น propagation จะมีรูรั่วตามทางที่ลืม — เพิ่มเคส test ครอบ "ปุ่ม → Buyer → logout กลาง" แล้ว
48. **[Web] cookie กันวน loop (marker) ที่ใช้ชื่อร่วมจะบังแอปอื่นบน host เดียวกัน** — อาการจากผู้ใช้จริง: login fintech → เปิด CIS ใหม่ SSO ได้ → เปิด Buyer ทันทีกลับถาม login (แต่รอบสองเข้า auto แบบมี delay) — สาเหตุ: marker `sso_try` (อายุ 30 วิ กัน loop /→login→/) เป็น cookie ของ host localhost → CIS set แล้ว Buyer ภายใน 30 วิ เห็น marker ของ CIS จึงข้าม redeem ไปหน้า login; รอบสองที่เข้า auto แบบมี delay เพราะรอบแรก login ผ่านหน้า upstream แล้วเกิด KC SSO session ใน browser → AC flow เดินเงียบ ๆ เอง — แก้: marker **แยกชื่อต่อแอป** (`sso_try_buyer`/`sso_try_cis`/`sso_try_portal`) — กัน loop ของใครของมัน ไม่บังข้าม — บทเรียน: cookie แชร์ข้าม port ทั้ง "โอกาส" (ตั๋ว SSO) และ "ภัย" (ชนกันเอง) ต้องออกแบบชื่อให้เป็นเจ้าของรายแอป
49. **[UX] ตั๋วตายต้องกลับหน้า landing ของแอป ไม่ใช่พาไปชนหน้า login ของ Keycloak** — อาการจากผู้ใช้จริง: session หมดอายุแล้วเปิด :3010 ระบบพาไปต่อหน้า login ของ KC ทั้งที่ผู้ใช้ยังไม่ได้ตัดสินใจ login — สาเหตุ: ทางเข้า `/auth/login` เมื่อ redeem ตั๋วไม่สำเร็จไหลต่อไป authorize ทันที และ branch ตรวจ liveness ตายก็ redirect เข้า `/auth/login` เช่นกัน — แก้: แยกสถานะ redeem เป็น **ok/dead/error** — dead (broker ปฏิเสธชัดเจน 404/403) = เคลียร์ cookie ตั๋วแล้ว redirect กลับ `/` (landing ของแอป ให้ผู้ใช้กดปุ่มเอง); error (broker ล่มชั่วคราว) = เดิน AC flow ปกติ (fail-open); และเพิ่ม UX: token หมดอายุแต่**ตั๋วยังอยู่** → renew เงียบ ๆ กลับเข้าระบบได้เลยโดยไม่ต้องกรอกรหัสผ่านซ้ำ — ประเด็นออกแบบ: หน้า landing ของแอปคือ "จุดตัดสินใจของผู้ใช้" ระบบไม่ควรพาข้ามโดยอัตโนมัติเมื่อไม่มี session ที่ใช้ได้
50. **[Arch] broker ต้องเป็นปลายทางด้วย + บั๊กอ่าน exp ของ JWT** — (1) ผู้ใช้เปิด ID Portal (:3000) ตรง ๆ แล้ว "นิ่ง" เพราะ portal เป็น broker แต่ไม่เคยเป็นปลายทาง — แก้: เพิ่ม `central-id-portal` ใน aud ของ scope `stt-bridge` (mapper ที่สอง), เลื่อน portal เป็น confidential + เปิด `standard.token.exchange.enabled`, login route redeem ตั๋วของตัวเองผ่าน **store ใน process เดียวกัน** (ไม่ยิง HTTP หาตัวเอง) แล้ว Token Exchange เป็น token `aud=central-id` + middleware auto-SSO/liveness ของ portal — (2) บั๊ก `jwtPayloadField`: เช็ค `len(parts) != 2` แต่ JWT แยกได้ 3 ส่วน → exp อ่านไม่ได้ทุกใบ → redeem ตกไปสาย renew ตลอด (ทำงานผ่านมาได้เพราะตั๋วจาก browser มี refresh token จึง renew แทนได้) — พอ test ด้วยตั๋วไม่มี refresh token จึงระเบิด — บทเรียน: ระบบ SSO มี "อย่างน้อย 4 บทบาท" (broker/ปลายทาง/ต้นทาง/ผู้ถือตั๋ว) ต้องไล่ครบทุกบทบาทเวลาเพิ่มความสามารถ
51. **[UX] i18n EN/ไทยแบบ lightweight ครบ 6 แอป — cookie `lang` แชร์ข้าม port เหมือน SSO ticket** — สลับได้ 3 ทาง: ปุ่ม `.langsw` ใน header ทุกหน้า · `?lang=en|th` (จำลง cookie 1 ปี) · cookie เดิม — ลำดับ ?lang → cookie → default **"th"** (เลือก default th เพื่อให้ test scripts ที่ grep ข้อความไทยยังผ่านทั้งหมด 162/162 หลังเพิ่ม i18n) — การแปลใช้ helper `T(lang, ไทย, English)` inline (คู่ข้อความอยู่ด้วยกัน ดูแลง่าย ไม่ต้องมี catalog ใหญ่) — Keycloak เปิด `internationalizationEnabled` + supportedLocales [en,th] (ธีมมี messages สองภาษาอยู่แล้ว หน้า login มี locale switcher ของ KC เอง) — cookie `lang` เป็น host-wide เหมือน `central_sso`: สลับที่แอปใดหนึ่ง → ทุกแอปบน localhost เปลี่ยนตาม (ยืนยัน: set en ที่ :3050 → :3000/:3010/:3020/:3040 render English) — ภาพ EN: screenshots ชุดใหม่ 01-30 ทั้งหมดถ่ายในโหมด English (cookie lang=en) · ข้อควรระวัง production: cookie host-wide ใช้ได้เพราะ same-host POC เท่านั้น (เหมือน SSO ticket)
52. **[Gateway] เขียน custom Kong plugin (oidc-central) เติมช่องว่างของ Kong OSS + แก้ DNS ช้าบน Docker Desktop (Windows)** — (1) jwt plugin ของ Kong OSS ตรวจได้แค่ signature+iss+exp จึงเขียน plugin **oidc-central** (Lua PDK — kong/custom/kong/plugins/oidc-central): ดึง JWKS จาก Keycloak (cache TTL 300s + kid-miss → force refresh รองรับ rotation), แปลง RSA JWK (n,e) เป็น PEM ด้วย DER encoder เขียนเอง (ระวัง: OID arc ใหญ่ เช่น 113549 ต้อง encode แบบ base-128 multi-byte), ตรวจ signature/iss/exp ด้วย **jwt_parser ของ Kong เอง** (resty.jwt ใน Kong 3.9 ไม่มี decode/load — เรียกด้วย colon เสมอ: jwt_parser:new(token)) และ **บังคับ aud + scope ที่ gateway** (403 audience mismatch / insufficient scope) — ตรวจแล้ว 12/12 รวมใน openapi-test.sh — (2) Kong resolve ชื่อ container ช้า 4-8s บน Docker Desktop (Windows) เพราะ default DNS order ลอง SRV ก่อน A แล้วโดน SERVFAIL ซ้ำ — แก้ด้วย env `KONG_DNS_ORDER: A` → 0.012-0.023s (~400 เท่า) — production notes: plugin นี้เป็น gateway-level pre-validation ไม่แทน Guard ของ service (defense in depth คงอยู่); cache per-worker — production ใช้ shm + fail-closed policy
53. **[Gateway] Introspection ที่ gateway + portal routing + hardening plugins (ADR-005)** — (1) **oidc-introspect** (custom plugin): ตรวจผ่าน Keycloak `/introspect` (RFC 7662) ด้วย client credential ของ partner-001 + cache 10s — ปิดจุดอ่อน JWKS ("revoke แล้ว token ยังใช้ได้ถึง exp") — ทดสอบ revoke จริง → request หลัง cache หมดได้ 401 "token inactive" — ข้อแลก: SLA = cache TTL + fail-open เมื่อ KC ล่ม (production: fail-closed + shm) (2) **portal routes** `/portal/id|buyer|cis` — เปิดทุก portal ผ่าน Kong :8000 ได้; ข้อจำกัด: redirect_uri/ลิงก์ภายในยัง hardcode port ตรง → login flow หลุดออกจาก Kong หลัง redirect แรก (production ใช้ hostname เดียว + ลงทะเบียนให้ตรง) (3) **hardening**: request-size-limiting 1MB → 413, cors preflight → Access-Control-Allow-Origin, prometheus + `KONG_STATUS_LISTEN=:8100` → `kong_http_requests_total` แยก service/route/status (4) **setup.sh injection order bug**: awk ตัวที่สองอ่าน template ทับผลแรก → RSA key หายจาก kong.yml — แก้ให้อ่านจากผลล่าสุด + เพิ่ม check "placeholder ค้าง = fail" — ทั้งหมดรวมใน ADR-005

54. **[Gateway] Central API Keys — ออก key ผูก scope จาก ID Portal ใช้กับ Open API / MCP (ADR-005 ส่วนขยาย)** — flow: ผู้ใช้สร้าง key บนหน้า `/apikeys` ของ ID Portal (เลือก scope จากชุด orders.*/projects.* — format `central_<random>` แสดงเต็มครั้งเดียว) → ใช้ header `apikey` ยิง Kong route `/openapi/apikey/*` → custom plugin `central-apikey` ตรวจ key กับ `POST /apikeys/validate` (cache 15s) → บังคับ scope ตาม method (GET→read_scope / POST→write_scope) → ผ่านไปด้วย gateway-trust header — ผลทดสอบ: reader key GET 200/POST 403 · writer key POST 201 · ไม่มี key 401 · revoke (cache หมด) → 401 — **MCP pattern**: MCP server ตรวจ key ด้วย validate endpoint เดียวกัน + บังคับ scope ต่อ tool (contract เดียวกับ Kong plugin) — จุดสังเกต: เพิ่ม/ยกเลิก key ที่ ID Portal ทันทีโดยไม่แตะ kong.yml (ต่างจาก key-auth) · production: เก็บ hash + DB + quota + audit — รองรับชื่อ header ทั้ง `apikey` (Kong default) และ `X-API-Key` (de facto ในวงการ) ผ่าน config `key_names` แบบ comma-separated
55. **[MCP] Remote MCP Server (Streamable HTTP) บน Buyer /mcp — auth ด้วย Central API Key + scope-gated tools** — ใช้ official MCP SDK (dynamic import กัน ESM/CJS clash; handleRequest cast เป็น node http types) โหมด **stateless** (transport/server ใหม่ต่อ request, GET/DELETE → 405) — auth: header `apikey` หรือ `Authorization: Bearer central_…` → ตรวจกับ ID Portal `/apikeys/validate` ต่อ request (POC: ไม่ cache — validate เป็น in-network call) — **tools ลงทะเบียนครบทุกตัว แต่บังคับ scope ตอน execute** (list_orders→orders.read, create_order→orders.write): scope ไม่พอ → isError:true พร้อมข้อความบอก scope ที่ต้องขอ (MCP UX มาตรฐาน) — ดีกว่ากรอง tools/list ตาม scope เพราะ deterministic ไม่มีกรณีกำกวม (unregistered → SDK ตอบ "not found") — ระวัง: transport.handleRequest คาด node http types (cast ด้วย as unknown as) และ client ต้องส่ง `Accept: application/json, text/event-stream` ตาม spec — ผล: 12/12 (mcp-test.sh)
