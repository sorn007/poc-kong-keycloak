## 3. ทดสอบด้วยหน้าจอ (จำลอง flow rootcase — อัปเดต 2026-11-13: 3 แอปเต็มรูป)

ระบบมี **3 แอปมีหน้าจอจริง**: **Central ID Portal** (:3000, Go Fiber — บัญชีกลาง: โปรไฟล์/แอปที่เชื่อมต่อ/session/logout กลาง, client `central-id-portal`, aud `central-id`), **Buyer Portal** (:3010, NestJS), **CIS Portal** (:3020, Go Fiber) และเปิดใช้ **Identity Brokering** (Option B ใน migration-plan): ผู้ใช้ login ที่ realm `central-id-upstream` (**"Central ID จริง" — ธีมเขียว**, จำลองระบบ Central ID เดิม — ตั้งโดย `scripts/setup-brokering.sh`) แล้ว realm `central` (Keycloak ซ่อนเบื้องหลัง) ออก token ให้แอป — ผู้ใช้ไม่เห็นหน้า login ของ realm central เลย ทุกหน้ามีแถบขั้นตอน flow ตาม rootcase: [1] ล็อกอิน Central ID → [2] Buyer Portal → [3] CIS Portal (SSO) → [4] Logout กลาง

ผลจำลองด้วย curl + cookie jar ตาม redirect ทุกขั้นเหมือน browser (2026-11-13):

1. ✅ เปิด Central ID Portal (:3000) → hero "Central ID — บัญชีกลาง" + ปุ่มล็อกอิน
2. ✅ Login → **โดนพาไปหน้า login ของ Central ID จริง** (upstream realm, ธีมเขียว) → กรอกรหัส → auto-link (Detect Existing + Auto Link, ผูก email กับบัญชีเดิมโดยไม่ถาม) → กลับมาเห็น "สวัสดี buyer-user" + token ครบ aud/principal_type/tenant_id
3. ✅ หน้า **แอปที่เชื่อมต่อ**: Buyer Portal / CIS Portal (เชื่อมต่อแล้ว + SSO) / Open API (M2M ไม่แสดง session)
4. ✅ เปิด Buyer Portal → SSO ทันที → dashboard + Orders (GET 200 / POST 201 ผ่าน cookie session)
5. ✅ เปิด CIS Portal → SSO ทันที → dashboard + Projects (GET 200 / POST 200)
6. ✅ **Logout กลาง** จากแอปใดก็ได้ (`client_id` + `id_token_hint` + `post_logout_redirect_uri` ลงทะเบียนครบ → ไม่ขึ้นหน้า confirm แล้วพากลับแอป)
7. ✅ Login ใหม่ที่ CIS → **กลับไปหน้า login ของ Central ID จริง กรอกรหัสจริง** (SSO ถูกยุติ)
8. ✅ **Playwright ถ่ายภาพจริงครบ 15 ขั้น** (ทุกภาพอยู่ที่ `docs/screenshots/` — รันซ้ำได้: `cd tools/screenshots && source ../../.env && node journey.mjs`)

หมายเหตุพฤติกรรมหลังมี brokering: (1) หลัง logout กลาง **access token เดิมยัง valid จน exp** และ session ของ Keycloak ที่ค้างในเครื่องเดิมยังใช้ได้ — production ต้องตั้ง **backchannel logout** จาก Central ID → Keycloak (rootcase §6); (2) logout จากแอป (RP-initiated logout ที่ realm central) ยุติ SSO session ของ Central ID ด้วย — Keycloak ส่งต่อเป็น Single Logout ผ่าน Identity Brokering ด้วย chain ของ redirect ที่ browser ตามเอง (client ที่ไม่ตาม redirect เช่น curl ธรรมดาจะเห็น session ของ Central ID ยังอยู่ — ไม่ใช่พฤติกรรมของ browser — ดู §4 ข้อ 63)

## 4. สิ่งที่พบระหว่างทดสอบ (2026-11-12 ถึง 2026-11-13)

1. **KC 26 ไม่มี field `keys` บน RealmRepresentation** — import RSA key แบบ static ผ่าน realm.json ใช้ไม่ได้ (สลับไปให้ Keycloak generate เอง + ดึง public key ผ่าน Admin API — ดู ADR-003)
2. **Mapper config key ต้องเป็นเอกพจน์บน KC 26.x** — `access.token.claim` / `id.token.claim` (รูปแบบเอกสารเก่าเป็นพหูพจน์ `access.token.claims` — ไม่มี legacy fallback ใน `OIDCAttributeMapperHelper.includeInAccessToken()` → mapper ถูกข้าม**เงียบ ๆ** ไม่มี log/error) — พิสูจน์จาก source 26.3.5 (`OIDCAttributeMapperHelper.java:386-392`)
3. **Realm import ที่มี `clientScopes` ชัดเจน จะไม่สร้าง stock scopes** (`basic`/`profile`/`email`/`roles`/`web-origins`/`acr`) และ `default-default-client-scopes` ว่าง — บน KC 26 `sub` ของ access token มาจาก **sub mapper ใน scope `basic`** (initToken ตั้ง sub เฉพาะ TRANSIENT session เช่น client_credentials) — realm ที่ import เองต้องใส่ stock scopes ใน template ด้วย (template ปัจจุบันผสมนิยาม stock จริงที่ export จาก realm ที่สร้างสดแล้ว)
4. **`jti` ของ KC 26.x มี prefix บอกบริบท** — รูปแบบ `sessionType+tokenType+grantType:uuid` เช่น `onrtro:` = online+regular, `trrtcc:` = transient+regular+client_credentials, `onltro:` = online+**lightweight** (ไม่ใช่ token เสีย — ดู source `DefaultTokenContextEncoderProvider`)
5. **KC 26 ตั้ง admin-cli/admin-console เป็น lightweight access token โดยดีไซน์** (`RealmManager.java:232` set `USE_LIGHTWEIGHT_ACCESS_TOKEN_ENABLED=true`) — token ของ admin-cli จึงไม่มี `sub`/claims ที่ mapper ไม่ได้ตั้ง `lightweight.claim` — เป็นพฤติกรรม stock ทุกเวอร์ชัน 26.x **ไม่ใช่ bug ของ instance**
6. **Kong 3.9 jwt plugin ใช้ config `key_claim_name`** (ไม่ใช่ `key_claim`) และ `rsa_public_key` ต้องเป็น PEM ที่มี header/footer ครบ — ค่า `publicKey` จาก Admin API เป็น base64 ดิบ ต้องห่อ BEGIN/END ก่อนใส่ kong.yml
